# 测试集提交版本说明

数据集：`/data/raw/contest_8/QA_test.json`，400 题。
官方计分：满分 1087。ES 按 ID 集合与顺序各占一半；PG 与跨源看执行结果是否非空；MySQL 与 SQLite 看结果集是否等价。
本地对照：拿 `/data/submit/gpt-v1/result.json`（官方约 900 分）当参照，用 `/data/lj/verify_sql.py` 逐题执行比对。「一致」指结果集和 GPT 相同。

四个提交版本共用同一套路由器、检索器和表卡片，差别只在生成器权重和提示词约束。

## 共用部分

| 组件 | 做法 | 位置 |
|---|---|---|
| 路由器 | Qwen3.5-4B LoRA，问题 → 数据源、库、表（跨源为两步） | `/data/k/runs/router-r0/v3-20261003-191238/checkpoint-730` |
| 表卡片 | 由 db.table 直接查表，含用途、字段、枚举、外键 | `/data/k/generator/schema_cards.json` |
| 知识检索 | 表字段说明按路由表全量取；业务规则用 Qwen3-Embedding-0.6B 取 top-3 | `/data/k/generator/knowledge.py` |
| 相似案例 | Qwen3-Embedding-0.6B 取 top-10，再过滤 | `/data/k/runs/test-full-v1/similar_top10.json` |
| 推理与提交 | 路由 → 检索 → 组提示词 → 生成 → 合并 → `result.json` | `/data/k/experiments/run_test_full.py` |
| 程序约束 | 表名核对、ES 查询类型、跨源 `result`、真实库执行 | `/data/k/experiments/guard.py` |

## v1：未微调基线

- 生成器是原始 Qwen3.5-4B。
- 提示词与训练集实验 E09 相同：表卡片 + 知识 + 2 条相似案例 + 按数据源区分的方言提示。
- 知识里 3 条检索规则全部放入，400 题全有规则。相似案例只要求同数据源。
- 没有生成后校验。68 题 SQL 执行直接报错，12 道跨源题全部失败。
- 典型错误：第 4 题「各车型总载重」被检索来的载重分段规则带偏，写成轻型/中型/重型分段。

## v2：四项免训练约束

在 v1 之上，生成器不变，只改提示词和程序：

1. 业务规则相似度低于 0.65 不放入，带规则的题从 400 降到 50。表字段说明保留。
2. 相似案例必须同一库，相似度不低于 0.6。373 题 2 条，10 题 1 条，17 题 0 条。
3. 生成后先静态检查再真实执行，失败把报错发回模型重写一次。412 次调用重写 90 次。
4. 跨源固定两步、第二步必含 `result`、不混 MySQL 与 PostgreSQL；ES 只允许 bool / geo_distance / geo_polygon / geo_bounding_box / term / range。

执行失败从 68 题降到 36 题，一致题数 183 → 204。第 4 题恢复为按车型 `SUM(load_capacity)`。

## v3：第一阶段 LoRA（当前最优）

- 生成器加载 `/data/k/runs/generator-e09/v0-20261004-182257/checkpoint-740`，第 2 个 epoch。
- 训练数据 `/data/k/runs/generator-e09/train.jsonl`，5920 行：知识用金标 `knowledge_ids` 原文，相似案例同数据源 top-2，三元组用标注，跨源拆成两步各一行。
- 超参：rank 8、alpha 16、lr 1e-4、4 epoch、全局批次 16、max_length 4096。
- 提示词和约束与 v2 相同。重写次数 90 → 33。
- 官方 636 分。一致 235 题，执行失败 13 题。单独执行成功率 391 / 400。

| 数据源 | 一致 / 结果不同 / 执行失败 |
|---|---|
| MySQL | 75 / 22 / 1 |
| SQLite | 85 / 112 / 2 |
| PostgreSQL | 32 / 6 / 0 |
| Elasticsearch | 35 / 6 / 9 |
| 跨源 | 8 / 3 / 1 |

## v4：第一阶段 LoRA 训满 4 epoch

- 同 v3，只把权重换成 `checkpoint-1480`。
- 训练损失 0.051 → 0.016，token 准确率 0.984 → 0.994，测试分反而从 636 掉到 538.5。
- 215 题 SQL 文本变了，SQLite 占 152 题。SQLite 一致 85 → 59，执行失败 2 → 16。
- 多出来的是训练题里的 WHERE 字面量：第 4108 题加了「凤凰城、星级 > 3」，第 4255 题加了 `review_stars = 5 AND review_votes_funny = 'Uber'`，题目里都没有。
- 结论：这套数据上第 2 个 epoch 是更好的权重，第 4 个 epoch 过拟合。

官方分项：SQLite 53/200 全对、142/569.5 分；MySQL 65/100、162.5/264.5；ES 46/50、125/137；PG 37/38、55/59；跨源 11/12、54/57。丢分集中在 SQLite 的 knowledge 类题（79/226 全对）。

## v5：第二阶段 LoRA（卡上正在训）

目标是让训练输入和测试输入完全一致，并教会模型看报错改 SQL。

- 训练数据 `/data/k/runs/generator-e09-sft2/train.jsonl`，5920 行，由 `generator/sft/export_jsonl_v2.py` 复用 `run_test_full.build_tasks` 导出，提示词与 v2–v4 测试时逐字相同。
- 与第一阶段数据的四处不同：
  1. 知识用检索器真实输出（表说明 + 相似度 ≥ 0.65 的规则），843 题带规则，2991 题带表说明。
  2. 相似案例同库且 ≥ 0.6：5383 题 2 条，201 题 1 条，246 题 0 条。
  3. 系统提示带上测试时的附加句（规则不在提示词里就不用、ES 禁 geo_shape、跨源两步说明）。
  4. 976 行失败重写多轮样本：首轮是 e09 在训练集上真实的错误 SQL（`loss=false`），用户发回真实报错，末轮为金标 SQL。10 条超长回退为单轮。
- token 最长 5155，`max_length` 6144，24 行超过 4096。
- 脚本 `generator/sft/train_v2.sh`：双卡、每卡批次 2、梯度累计 4、全局批次 16、4 epoch、每个 epoch 存权重。每卡批次 4 会在长样本上超出 40GB。
- 输出 `/data/k/runs/generator-e09-sft2/v4-20261005-094854/checkpoint-*`。
- 出提交时取第 2 个 epoch 的 `checkpoint-740`，v4 已经证明训满会掉分。

这一版能缓解「照着无关规则加条件」和「执行失败后改不对」，压不住「把训练 SQL 的过滤条件背到测试题上」。

## 仍未覆盖的差距

以 v3 的 SQLite 112 道结果不同的题归类：

| 差异 | 题数 | 例子 |
|---|---|---|
| 表集合不同 | 75 | 第 3069 题「年初至今销售额」有现成列 `ytd_sales`，模型去 join 明细表 |
| 输出列不同 | 16 | 第 3487 题问「最高是多少」，应 `MAX()`，模型列出每行 |
| 聚合口径不同 | 14 | 第 3100 题「多出百分之多少」应 (A−B)/B，模型写 A/B |
| 多写过滤条件 | 7 | 第 3281 题问生日，多加了击球手、投球手条件 |

后续方向：提示词补列选择与聚合口径规则；程序扫 WHERE 字面量并重写；每个 epoch 用测试集选权重；评估换 14B 生成器。
